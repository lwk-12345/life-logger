## 2026-09-23 · 全文优先，事件只留确定点

- **决策：** 把完整 ASR 转写设为长期主资产，默认同时保存结构化 `transcript.json` 和人可读 `transcript.md`；事件契约不删除，但只接收高置信、语义自足的确定点。
- **数据支撑：** 真实 9 月 21 日任务的 ASR 全文有 632 段，而声源筛后的 result transcript 只有 45 段；收敛计划同时记录过“8 个提取事件、可用 0 个”，误判集中在半截话和上下文依赖口语。
- **否掉的方案：** 继续把日常口语尽量切成 routine / work / idea 等离散事件，再靠低置信 review 修补。
- **为什么：** 口语天然不自足，强行结构化会丢上下文甚至制造语义。全文保留后，搜索/回看/后续 AI 都还有原始文本证据；事件只承担少量确定索引点，因此“不编造”与稳定事件契约可以同时成立。

## 2026-09-23 · 删除 structured_qa

- **决策：** 删除 `structured_qa.py` 和 `/api/qa`，保留底层 search / stats 原始能力。
- **数据支撑：** 收敛计划已经确认，结构化问答不调用模型，本身不能完成真正的推理；同时当前真实提取数据质量不足，项目曾出现“8 个提取事件、可用 0 个”的结果。
- **否掉的方案：** 继续把规则拼装出来的答案包装成“结构化问答”，或继续给它补更多问句模板。
- **为什么：** 当上游数据不可靠时，“带证据的假答案”比明确没有答案更危险。搜索和统计仍可作为事实接口交给外部 Agent 按需使用。

## 2026-09-23 · 删除 push_adapter 与 brief push bridge

- **决策：** 删除 `push_adapter.py`、`brief_push_bridge.py`、`brief_webhook_example.py`，保留 `daily_brief` 的本地 outbox 与直接 webhook 接缝。
- **数据支撑：** 收敛计划确认这套代码是在一个很薄的输出接口外再包一层适配器；核心需求只是让外部 Agent 能消费 daily brief。
- **否掉的方案：** 继续维护 provider/adapter 抽象，为未来微信或其他推送产品预先设计统一桥。
- **为什么：** 当前只有一个真实消费者方向，抽象层没有降低实际复杂度，反而增加维护面。目录 outbox + 简单 HTTP webhook 已经足够形成稳定边界。

## 2026-09-23 · 删除 multi_speaker_identity prototype

- **决策：** 删除 `multi_speaker_identity.py` 原型，保留现有 self / non_self / unknown 声源归属主逻辑。
- **数据支撑：** 收敛计划确认该模块从未进入默认主链，只是独立 prototype。
- **否掉的方案：** 在还没有多人身份真实使用场景前，把 prototype 升级成正式身份库和多人识别链。
- **为什么：** 主问题仍是“这段是不是我说的”，不是“所有人分别是谁”。先守住当前声源归属主链，避免为未验证场景扩展状态和 UI。

## 2026-09-23 · 删除 image_ingest

- **决策：** 删除 `image_ingest.py` 与 `/api/image-candidates`。
- **数据支撑：** 收敛计划记录本机没有产生 `image-candidates.json`，也没有真实图片候选数据。
- **否掉的方案：** 保留图片作为第二输入源，继续补图片候选审核、API 和 UI。
- **为什么：** 一个没有真实数据的第二输入源只会扩大系统表面积。当前首先要证明音频这一条主路径能产生值得回看的记录。

## 2026-09-23 · 删除 mobile_shell

- **决策：** 删除 `mobile_shell.py`、`mobile-shell/` 和独立壳验证脚本，移动访问继续使用现有 Web/PWA。
- **数据支撑：** 收敛计划确认自用移动端已经可以沿现有 Web 路径使用，独立原生壳意味着另一条构建和维护链。
- **否掉的方案：** 同时维护 Web 控制台与轻量原生壳，把“像 App”作为当前阶段目标。
- **为什么：** 当前目标是降低自用摩擦，不是增加客户端形态。已有 Web 能满足入口需求时，第二套壳没有验证出额外价值。

## 2026-09-23 · 删除 personal_adaptation

- **决策：** 删除 `personal_adaptation.py`，主链回到通用 CAM++ + 上下文声源判断；历史 personal JSON 保留但不参与运行。
- **数据支撑：** 收敛计划指出该机制依赖“每天使用 + 每天复核”的闭环，而实际复核队列为空，前提没有成立。
- **否掉的方案：** 继续扩充个人声音原型、场景分类和自动训练池，希望以后使用量上来后再体现价值。
- **为什么：** 没有持续反馈数据时，自适应系统只是增加状态和不可解释性。先保留无需人工训练才能工作的声源判断主链。

## 2026-09-23 · 删除 cold_start + sample_harvest

- **决策：** 删除 `cold_start.py` 和 `sample_harvest.py`；历史 cold-start / sample-harvest JSON 保留，但不再生成、不参与运行或复核 UI。
- **数据支撑：** 收敛计划确认两者依赖的个人化训练闭环前置条件没有成立。
- **否掉的方案：** 继续自动采样、积累候选，再期待人工逐步确认形成训练集。
- **为什么：** 上游 personal adaptation 已经没有真实闭环，这两层继续存在只会制造待复核库存和额外流程，不会提升当前自用价值。

## 2026-09-23 · 删除 multi-source time_calibration

- **决策：** 删除多源 `time_calibration.py`；开始时间只接受用户显式时间或文件名中的墙钟，否则标记为 unknown。
- **数据支撑：** 项目已经遇到真实反例：容器 metadata 的 `creation_time` 接近录音结束/封装时间，却曾被当成开始时间，导致整段事件被错误平移到下一天。
- **否掉的方案：** 继续维护 metadata / sidecar / filesystem mtime 等多源优先级与置信度规则。
- **为什么：** 对日记系统来说，“不知道绝对时间”比猜错一天更安全。时间来源越多并不等于越准确；没有可靠语义的 metadata 不应被提升为录音开始证据。

## 2026-09-23 · 小苏/微信只认一个 outbox + 一个 brief API

- **决策：** 外部消费边界固定为一个本地 outbox `output/local-web/outbox/daily-brief/` + 一个只读 `GET /api/daily-brief`；可选 webhook 只直发同一份 `agent-brief-v1`。
- **数据支撑：** provider/adapter 抽象已被删除；当前真实消费方向就是手机 + 微信 + 小苏。零配置 Demo 能生成 5 个高置信结构点的 outbox，并自动验证不包含原始音频/证据字段。
- **否掉的方案：** 为微信、OpenClaw、Hermes 分别做 provider/adapter 工厂；把 `/api/search`、`/api/jobs` 等开发接口都纳入必须维护的消费协议；把全文转写或原始音频直接推送出去。
- **为什么：** 一个 allowlist payload 同时覆盖目录、HTTP 和可选 webhook，既减少集成维护面，也缩小第三方隐私暴露面。深度搜索仍可留作本地开发能力，但不是小苏/微信的稳定数据契约。

## 2026-10-14 · MOSS 声纹换 CAM++，打分粒度改为「按说话人合并」

- **决策：** MOSS 主路径的声纹后端从「48 维手工频谱包络」换成 CAM++（funasr，**同进程**加载，192 维）；打分粒度从逐 span 改为按 (chunk, MOSS 说话人) 合并成长段算一次、分数回填给组内每段；48 维保留为「funasr 装不上 / 权重不在」时的降级路径；两套阈值打包成 `VoiceprintPolicy` 按**生效后端**成套取（CAM++ 0.40/0.30，48 维 0.50/0.25），可用 `local-config.json` 的 `moss_voiceprint` 或 `LIFE_LOGGER_MOSS_*` 覆盖。
- **数据支撑：** 207 条真实 rows：48 维把 AI 技术视频判成本人（段 000024 给 0.650，CAM++ 给 -0.024），合并粒度把分离间隔从 0.244 拉到 0.440（视频中位 0.195 / 本人中位 0.635）；端到端实测（`scripts/probe_moss_campplus_e2e.py`，真音频 + 真权重）视频 0.147/0.158 判 non_self、本人 0.589/0.750 判 self。
- **否掉的方案：** 用子进程跑 CAM++（worker venv 里本来就有 funasr，声纹一直在调用进程里算，不需要）；沿用 0.45/0.25（跨量纲，会把非本人判成 self）；保留逐 span 粒度。
- **为什么：** 声纹的价值只在「非本人不被判成 self」，48 维在远场手表录音上做不到这一点；CAM++ 是同进程就能拿到的判别式模型，成本只有每文件 ~1s 加载 + 每组长窗 <1s。
